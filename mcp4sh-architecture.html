MCP4SH™ architecture

Designed to scale

Haptics should not need to be rebuilt every time the game changes.

Different simulators expose different data. Different hardware expresses sensation differently. The physical meaning in between does not need to start from zero every time.

MCP4SH is built as a semantic telemetry-to-haptics layer: specialised where the source or hardware requires it, consistent where the physics means the same thing. The current product is delivered through SimHub, but the architecture is deliberately separated so the interpretation and orchestration logic is not defined by one renderer or one device class.

Preserve meaning. Adapt the carrier.

01 · The architecture

Different sims. Same physical world.

One simulator may expose a direct signal. Another may provide richer tyre data. Another may require the same physical state to be derived from several related inputs. MCP4SH does not pretend those sources are identical.

The design goal is to understand those differences at the input, translate them into a consistent description of what the vehicle is doing, coordinate that information, and only then express it through the available hardware.

Normalize meaning, not information. Richer telemetry should stay richer. What becomes consistent is the semantic contract downstream.

02 · Fidelity without fragmentation

Specialise at the edges. Standardise the meaning.

A title-specific adapter can remain as specialised as necessary. The mistake is assuming that every downstream effect and every output device must then become title-specific too.

Use the best source available

Native signals, derived relationships and graceful fallbacks can all contribute without pretending they have identical fidelity.

Preserve useful spatial detail

Where per-wheel or directional information exists, it can remain spatial rather than being flattened into one chassis-level number.

Degrade honestly

Where a title exposes less, MCP4SH should communicate less precision rather than inventing detail that is not there.

03 · Orchestration

The vehicle is one system. The haptics should behave like one too.

Braking changes load. Load changes available grip. Suspension movement affects chassis behaviour. Engine, drivetrain, road, impact and tyre information all coexist. Simply making every lane louder at once does not necessarily communicate more.

MCP4SH therefore treats effects as parts of a coordinated tactile scene. Interpretation determines what the signals mean; orchestration decides how useful information should coexist when several things are happening at the same time.

Interpret

Work out what the available telemetry says about the current physical state.

Prioritise

Keep important transient or state information from being buried by continuous activity.

Express

Render the resulting semantic information through the capabilities of the target hardware.

More output is not automatically more information.

04 · Setup and tuning

Tune the rig. Not every game.

Transducers, mounting, resonant range, amplifiers, placement and personal preference still matter. No software removes the physical differences between rigs.

What MCP4SH is designed to remove is unnecessary repetition. Once hardware is mapped and calibrated, changing simulator should not mean rebuilding tyre, brake, suspension, drivetrain, road and load behaviour from scratch.

05 · Latency

Fast matters. Latency is not the whole haptic system.

Lower transport latency is desirable. Discrete events such as impacts, kerbs and sudden interventions benefit directly from the fastest practical signal path.

But useful tactile response also depends on what was detected, when the underlying state became meaningful, how it was interpreted, what else was happening at the same time, and whether the output communicates the correct thing.

Some cues are events. Others are states developing over time: load builds, brake pressure changes, grip evolves, suspension settles and drivetrain tension rises and falls. A state-aware system can begin changing the tactile representation while that condition develops instead of waiting for one final binary threshold.

useful state becomes detectable
later threshold / discrete event
Fast reaction is useful. Earlier understanding can be better.

This does not make transport latency irrelevant and MCP4SH does not claim to predict events that the simulator has not exposed. It means that an evolving physical state can carry useful information before a later event threshold is crossed.

06 · Scalability

What happens when there are more sims, more devices and more modalities?

A strong solution for one simulator and one output is a tractable problem. Maintaining coherent behaviour across an expanding ecosystem is a different one.

MCP4SH is designed so a new simulator primarily needs an input path capable of translating its available telemetry into established semantics, while a new hardware platform primarily needs a projection layer capable of expressing those semantics through what the device can physically do.

Repeated bespoke combinations

Game A → Device 1 Game A → Device 2 Game B → Device 1 Game B → Device 2 Repeat as both sides grow

Semantic layer

Games → specialised input adapters Shared interpretation + orchestration Outputs → specialised renderers Add capability at the edge
Add an input once. Add an output once. Connect through meaning.

Real integrations are never literally free. Individual simulators and devices still have unique capabilities and constraints. The architectural goal is to keep those differences at the edges instead of multiplying bespoke interpretation throughout the whole stack.

07 · Built for integration

The current SimHub plugin is an implementation, not the intended boundary.

Today, SimHub provides an excellent host for telemetry access, configuration and tactile output. MCP4SH.Core already separates most haptic interpretation and stateful effect logic from the host-specific plugin layer.

That boundary is deliberate. The longer-term direction is to let the same semantic and orchestration logic feed different hosts, SDKs and physical outputs without requiring the interpretation model to be rewritten around each one.

MCP4SH is not being designed around owning every input, every device or every transport. It is being designed to connect them.

08 · For hardware makers

Build the hardware. Do not rebuild the physics interpretation stack.

A transducer manufacturer should not need to become a specialist in every racing simulator. A pedal manufacturer should not need to reinvent braking, lock, traction and load interpretation title by title. A new output modality should be able to concentrate on how it expresses information rather than first recreating the meaning of that information.

The intended integration model is hardware-neutral: different devices should remain different. Their language does not have to be.

10 · Domain portability

A useful abstraction should survive beyond the first domain it was built around.

MCP4SH began with automotive simulation. The v1.2 development track is now testing how much of the same architecture can carry into flight: shared physical ideas such as powerplant behaviour, body load and transients, alongside airframe-specific semantics where the domain genuinely differs.

The goal is not to relabel automotive effects as aircraft effects. It is to reuse the parts of the interpretation model that represent transferable physical meaning and add new domain semantics where needed.

New domain. Same language where the physics overlaps.

Design principle

Specialise at the edges. Standardise the meaning.

Different simulators deserve access to their unique telemetry. Different hardware deserves to use its unique capabilities. Neither requires rebuilding the entire interpretation stack between them.

That is the problem MCP4SH is designed to solve.
